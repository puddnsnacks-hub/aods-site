Keeping Figma in sync with AODS

How a new AODS build becomes an update to the Figma library, how to read what the update did, and what to do when a Figma component does not match the real one.

Every topic on this page is written twice. The technical block is the reference: commands, files, counts, terms — for whoever runs the build and the plugin. The plain-language walkthrough under it is folded shut; open it for what the thing is, why it is done this way, and the steps in everyday words — for a designer who uses the library and wants to understand what happens to it.

Section 1 of 5

Where the Figma library comes from

Technical

Figma is a build target of the design system, not a second source of truth. Nothing in the library is authored in Figma: the same source that emits dist/tokens.css and dist/aods.css emits the library, and one plugin applies each release to one long-lived library file, in place.

tokens/g.json  s.json  c.json          # the three tiers
components/registry.json  aods.css       # the contracts and the CSS
build/figma_plan.json                   # what the registry cannot say: axes, state recipes, splits, specimens
        │
        ▼  python3 build/build.py        # dist/tokens.css · aods.css · manifest.json · tokens.json
        ▼  python3 build/gen_figma.py    # dist/figma/figma.json — THE PLAN (+ report.md)
        ▼  python3 build/render_figma.py # dist/figma/nodes.json — THE DRAWINGS (+ render-report.md)
        ▼  dist/figma/plugin/            # the plugin, with the release inlined
        ▼  Figma · Plugins · AODS · apply release  →  the library file

Identity is what makes the update in place possible. Every node the plugin makes carries its key in shared plugin data (aods / key, e.g. comp:card::Emphasis=4, Density=comfortable, Interactive=false, Variant=default, Surface=light); the file root carries the ledger (aods / ledger, in parts) and the release version + sourceHash (sha256 of the inputs, first 16 hex). Variables are named by token path (button/primary-fill) and codeSyntax.WEB is the real var(--c-button-primary-fill), so Dev Mode shows the name a builder writes.

The long form — the IR schema, the mapping in full, what does not map — is FIGMA.md.

Why can’t we just draw the components in Figma and keep them there? Learn more

What

The AODS components are real, running code: a card is a piece of HTML with a stylesheet, and every color, size and spacing in it comes from a named token (a value with a name, like c.card.inset = 24px). The Figma library is a copy of those running components, drawn automatically. A script opens each component in a hidden browser, measures exactly what the browser painted, and writes down which token produced every fill, stroke, gap and font. A second program — the plugin — rebuilds that in Figma, binding each measurement to the matching Figma variable (Figma’s word for a named value) or text style.

Why

If the library were drawn by hand, it would be a second thing to keep true. Every token change, every fix to a component, every new variant would have to be repeated in Figma by someone who noticed — and over months the two drift until nobody knows which one is right. Generating the library from the code means there is one truth, and Figma follows it. It also means a designer can trust that what the library shows is what the site will actually render.

How

  1. Someone changes the system — a token value, a component’s CSS, a contract in the registry.
  2. The build runs and turns that into the shipped CSS.
  3. Two scripts turn the shipped CSS into a Figma plan (which collections, styles and sets exist) and the drawings (every variant, measured).
  4. The plugin reads both and updates the library file — the same file every time, changing only what changed.
Analogy — A printed brochure comes out of a layout file. When a phone number changes you do not correct it on the printouts with a pen; you change the file and print again. The Figma library is the printout. The tokens and the CSS are the file.

Section 2 of 5

Sync a new build into the library

Technical

The recommended route is the plugin: one click applies a whole release and needs no assistant in the loop. Build the release first, from the source repository:

python3 build/build.py                 # must end "errors 0"
python3 build/gen_figma.py             # the plan: dist/figma/figma.json (+ report.md)
python3 build/render_figma.py          # the drawings: dist/figma/nodes.json (+ render-report.md) — ~13 min, needs Playwright's Chromium
python3 build/audit_figma.py           # optional: binding coverage → dist/figma/audit.json
node figma-plugin/test/run.js          # optional, seconds: applies the release twice to a mock Figma; must say "idempotent: YES"

Both Figma scripts re-bundle dist/figma/plugin/ with the release inlined into ui.html, because a development plugin cannot read files beside itself. Then, in Figma desktop, in the library file:

  1. Once: Plugins → Development → Import plugin from manifest… → dist/figma/plugin/manifest.json. Figma reads the plugin files from disk every time it runs, so a later build needs no re-import.
  2. Plugins → Development → AODS · apply release. The window shows the release it carries (name, version, generated date, source hash, counts, and “N of M variants rendered”) and what the file already holds (collections, text styles, pages, the ledger’s version and last applied time).
  3. Leave the five phases ticked — variables · text styles · icons · components · docs — leave purge retired off and the only field empty. Apply release.
  4. Read the summary (Section 3). If it lists problems, resolve them and apply again; re-applying is safe.
  5. Publish the library through Figma’s own publish flow (Assets → Libraries → Publish). Put the release version and source hash in the description, e.g. AODS 2.1.0 · 70b3c573b58b4020.

What an apply does to what is already there

  • Same release again: creates nothing. Variables, styles and sets are found by key and left in place; variant contents are repainted identically.
  • A new release: variable values, text styles and variant contents are updated in place — the ids survive, so every instance in every consumer file keeps its bindings. New components and variants are created. Anything the release no longer lists is retired: a variable or style is renamed with a ⌫ prefix and hidden from publishing; a variant is moved to the Retired page. Nothing is deleted unless purge retired is ticked.
  • A release that renames tokens carries build/figma_renames.json ({"c.button.primary-fill": "old/name/in/figma"}, from audit/RENAME-MAP.json): the plugin renames the variable instead of creating a new one, and bindings survive.
  • A partial apply: type component ids in only (button card) to rebuild just those sets. Variables, styles and icons are still applied in full so the components have something to bind to.
  • The canvas is re-laid, every time: each set's table, its ground sheet and dark panels, the section's size, and the order of sections down the page. A section that grew moves the ones below it instead of covering them. Anything moved by hand in the library file goes back on the next apply — arrange instances in your own files, not the library.

Apply per release tag, never between two. The render is the slow step; run it where Playwright’s Chromium is installed (the container, like check_lead.py) and copy dist/figma/ across.

What actually happens when I press Apply? Learn more

What

“Apply release” is a reconcile, not a paste. The plugin walks through everything the release describes — every variable, text style, icon and component variant — and for each one asks the file: do you already have this? It finds things by a key it wrote onto them the first time (a hidden label such as comp:card::Emphasis=4, …), never by position or by what they look like. If the thing exists it is updated where it stands; if it does not, it is created; if the file has something the release no longer mentions, it is set aside, not thrown away.

Why

Designers build pages out of instances of the library’s components. An instance is a link back to the component; if the component were deleted and re-created, every page using it would lose the link and turn into a loose drawing. Updating in place keeps those links, so a page made last month picks up this month’s fix automatically. Retiring instead of deleting means a mistake in a release can never silently destroy someone’s work.

How

  1. Ask whoever runs the build for the release — or run the five commands yourself if you have the source repository and a Chromium for the renderer.
  2. Open the library file in Figma desktop (not a copy, not a branch).
  3. Plugins → Development → AODS · apply release.
  4. Check the release card says the version you expect and “1347 of 1347 variants rendered”.
  5. Apply. Watch the progress bar; a full release takes a few minutes.
  6. Read the summary, then publish the library so everyone gets the update.
Analogy — Updating a contact card in your phone rather than deleting the contact and making a new one: everyone who saved that person keeps working, and the number is simply the new number now.

Section 3 of 5

Read what the apply did

Technical

The plugin ends with a summary in four groups — created · updated · retired · problems — counted by kind: collection, mode, variable, text style, page, section, component set, variant, icon, text property, instance-swap property, doc frame, cover. Two reference points for release 2.1.0:

RunCreatedUpdated
first apply, empty file3 collections · 3 modes · 2,229 variables · 73 text styles · 9 pages · 73 sections · 41 icons · 68 doc frames · 85 component sets · 1,347 variants · 118 text properties · 13 instance-swap properties · 1 cover—
the same release againnothing3 collections · 73 text styles · 41 icons · 85 sets · 1,347 variants

A “created” count on a second run of the same release is a bug report, not a result — file it with the summary.

Problems, and what each means

  • … no rendered tree for <variant> — nodes.json lacks that variant. Re-run render_figma.py (for one component: python3 build/render_figma.py card), then gen_figma.py, then apply.
  • fonts not available in this file, Inter used instead: … — a face Figma could not load; the text was built in Inter so the run could finish. The system’s faces are Outfit, Newsreader, Lato, IBM Plex Sans, IBM Plex Mono and Geist Mono. Install the missing one (Figma desktop reads local fonts) and apply again.
  • <set>: text property <Name> — … — Figma refused a component property; the message is Figma’s own.

The three reports that ride with a release

  • dist/figma/report.md — from the planner: every place the two worlds do not map one to one (errors, warnings, notes).
  • dist/figma/render-report.md — from the renderer: findings per component, the observed text styles (a text the browser set in a tuple no planned style names, e.g. ui/md/regular/~24-0.1: a role whose leading or tracking inherits the page’s rather than naming a token), and the absolute-position fallbacks (a layout the renderer could not express as auto-layout, drawn at measured positions).
  • dist/figma/audit.json — binding coverage over the drawings. At 2.1.0: fills 99.7 %, text fills 100 %, padding 99.8 %, gaps 99.2 %, stroke colors 94.6 %, stroke widths 99.6 %. Radius (35.5 %) and size (52.8 %) are low by design: radius is 0 almost everywhere by rule, and most sizes are hug or fill.

The file itself remembers: the plugin’s file card reads aods / version and the ledger from the document root, which is how it knows what is already applied before you press anything.

How do I know the update worked, and what do the numbers mean? Learn more

What

The summary is a receipt. Created is what the file did not have and now does. Updated is what it had and which was refreshed. Retired is what the release dropped and the plugin set aside (renamed with a ⌫ mark or moved to a page called Retired). Problems is anything it could not do, in plain words. Alongside the receipt come three written reports from the build itself, listing every place the code and Figma could not be made identical.

Why

Without the receipt you would have to hunt through 1,347 variants to see whether anything changed. With it, a healthy update reads at a glance — a new release shows updates and a few creations; the same release twice shows no creations at all. The reports matter because they are where the next improvements come from: an “observed text style” is the build telling you a text role is missing a token, before any designer notices the wrong leading.

How

  1. After Apply, read the four groups. Zero problems is the goal.
  2. If a problem names a font, install that font and apply again.
  3. If a problem names a variant with no drawing, the renderer has to run again — pass the message to whoever runs the build.
  4. Open the Retired page occasionally: it should be empty or contain only things you expected to disappear.
  5. Skim render-report.md once per release; anything under “observed text styles” is a token decision waiting to be made.
Analogy — A delivery slip: what was dropped off, what was swapped for a newer model, what was taken back, and a note about the parcel that would not fit through the door.

Section 4 of 5

When a Figma component does not match the real component

Technical

Never correct a generated component in Figma. On every apply the plugin removes each variant’s children and paints them again from nodes.json; a hand edit lives until the next release and then vanishes without a trace. Variable and style names are reconciled by key, so a hand rename is reverted too. The library is an output. Fix the input, rebuild, apply, and Figma follows — that is the whole method, and it is why a fix made once is a fix made everywhere.

First establish which of two things is true: Figma differs from the browser, or Figma and the browser agree, and both differ from the intent. The browser’s own render of any variant is one command away and lands in dist/figma/ref/:

python3 build/render_figma.py card --ref --limit 4    # the browser's PNG per variant → dist/figma/ref/comp-card-….png; the rest of nodes.json is carried over

Put that PNG beside a screenshot of the Figma variant (select it → Export, or the MCP’s get_screenshot). Then triage:

How to report one

Record the variant’s key (it is the variant’s name inside the set, and the aods / key on the node), the two images, and which row of the table you think it is. Findings the renderer already knows about are in render-report.md; a human-found mismatch goes to the hit list in audit/ like any other system finding. The recent precedent: the card’s chamfered feature edge (clip-path: polygon) rendered in Figma as a straight bar — the fix was one function in the renderer, verified with --ref, and re-applied to the one set as a delta.

What is safe to do in Figma

Everything a consumer does: place instances, set the text and swap properties, override an instance in your own file, detach an instance in your own file. Nothing an author does: no edits to the library’s components, no renaming of variables, styles or sets, no new variants by hand, no rearranging of sets or sections (the apply puts them back). The ground sheets under the sets are locked rectangles the apply redraws; they are not part of any component and never travel with an instance. A component that needs to exist and does not is a request against registry.json or figma_plan.json.

Why can’t I just fix it in Figma — and where do I fix it instead? Learn more

What

Every component in the library is regenerated on every update: the plugin empties it and draws it again from the measurements. So a change made by hand in Figma is not wrong, exactly — it is temporary. It disappears the next time anyone applies a release, and nobody will know it was there. The place a correction lasts is upstream: in the token (a value), in the component’s CSS (its shape and behavior), in the plan (which variants exist), or — when Figma alone is wrong — in the translator that draws Figma from the code.

Why

Because the whole point of generating the library is that there is one truth. A fix upstream reaches the website, the documentation and Figma at the same time; a fix in Figma reaches only Figma, and only until the next release. It is also how the small things get caught: when the translator mis-draws a chamfer once, fixing the translator fixes it for every card, every release, forever.

How

  1. Open the real component beside the Figma one. The style guide and the component reference on this site show the running thing; the build can also write a picture of any single variant for you.
  2. Decide: does Figma look different from the browser? Or do they look the same, and both look wrong to you?
  3. If Figma is the odd one out, the translator is at fault — report it with the variant’s name and the two pictures. That is a build fix, and a quick one.
  4. If both are wrong, the design itself needs to change — a token value or the component’s CSS. That is a normal design-system change, made once, and Figma follows on the next update.
  5. If a variant is missing (say, a state you need), that is a request against the plan, not something to draw by hand.
  6. Never edit the library’s components directly, and never rename a variable or a style — the next update puts the old name back.
Analogy — A thermostat and a furnace. If the room is cold, taping a new number over the thermostat display changes nothing but the display. Fix the furnace (the code) and the display (Figma) reads right on its own.

Section 5 of 5

Verify a fix before you publish

Technical

Three checks, in this order, before a corrected release goes to the library — each is seconds except the render:

python3 build/build.py --check                        # the system's own lint: errors 0
python3 build/render_figma.py card --ref --limit 4    # the browser's PNGs for the component you touched
node figma-plugin/test/run.js card                    # the mock: applies twice, must say "idempotent: YES"

Then apply with only set to that component and compare a Figma screenshot of each changed variant to its PNG in dist/figma/ref/. The mock catches API misuse — a FILL outside auto-layout, a color without alpha, an alias to nothing, a variant name that is not Prop=Value, a negative radius or stroke weight, an opacity outside 0–1, a plugin-data entry over 100 kB, removing the current page, a layout property on a rectangle or a text, a min or max size on a node outside auto-layout, the synchronous accessors the plugin’s dynamic-page mode forbids — but it does not render; the picture comparison is the visual check and the only one.

Find the drift by the numbers

Screenshots find the drift you already suspect; the check finds the rest. build/drift_figma.py writes a script for use_figma that carries the expected geometry of a batch of variants and compares it against the file inside Figma — size, position, visibility, the frame’s layout mode, each child’s sizing modes, a text’s auto-resize — and returns only the disagreements, grouped by set with the recurring shapes first. It is what the auto-layout faults show up as: a frame that hugs nothing, a fill where the browser drew a hug, an indicator on the wrong edge.

python3 build/drift_figma.py script Wayfinding         # a use_figma script for the whole page (a set is sent as its axes + one drawing index per combination)
python3 build/drift_figma.py save Wayfinding r0.json   # what the script returned
python3 build/drift_figma.py report Wayfinding         # dist/figma/drift/Wayfinding.md — sets ranked by worst disagreement

Tolerance is 1 px (3 px for text, for frames that hug text and for a hugging root, whose advance Figma and Chromium measure a pixel apart). A finding is a class, not an opinion — root, size, pos, missing, hidden, layout, sizing, autoresize, and for a container gap, padding, align — and the container is judged first: when a frame’s own auto-layout settings disagree, its children’s positions are its finding, not theirs. Every finding so far has had its cause in the renderer or the plugin, never in the file. Run it after every apply; a clean page is the proof the release matches its drawings.

The plugin ends every run with the same reading of its own work: settleAll walks each variant against its drawing once every size is final — it re-asserts any child sizing Figma has changed since it was set, puts every absolutely positioned child back at its drawn box and only then pins it as its insets say, and locks each ratio box at its final width. Constraints and ratios set while a frame is still being built are measured against the frame’s size of the moment (a hugging card is 50 px taller for the instant its accent bar is a flow child), which is how a 170 px bar came out 120 and a 16:9 media 14 532 px tall (2026-09-14). The summary says how many settings it put back and where, how many children it pinned, and whether a flipped sizing was already off right after its variant was painted.

The third run’s other lesson is definiteness: a FILL child fills only a definite size. Under a hugging parent, or a FILL that hangs off one, a main-axis FILL contributes nothing to the hug and Figma squeezes it — the hero’s two flex: 1 buttons came out 69 px in a 147 px row. The renderer decides this once, from the root down, so a row that only becomes a hug because of its own parent still gets hugging children; across the main axis a FILL frame stays FILL, since Figma stretches it to the widest sibling exactly as CSS stretches a block.

The fourth run refined that with two facts probed in Figma itself. Figma shares FILL space between siblings’ content boxes — a padded FILL child gets its share plus its padding, where a 1fr 1fr grid gives equal border boxes — so where FILL siblings differ in padding the renderer hands each one’s padding to a paint-less FILL wrapper inside it (the hero’s inner padding) and the row splits as the browser split it. And Figma measures a FILL wrapping row at min-content when a parent hugs it, its widest single item, where CSS measures the row end to end: a FILL frame across the main axis whose max-content reaches its parent’s content width hugs, and a narrower one stays FILL and is definite after all, because a sibling settles the hug. The same run taught that a one-line text whose glyphs reach its block’s edges sized that block and hugs (as a FILL, Figma’s wider Lato wrapped it), that a definite flex-basis with no grow is the item’s width, and that a child a negative margin pulls above its container leaves its siblings a margin wrapper and takes the overlap out of the previous sibling’s trailing padding.

The file is a library only once it is published, and a publish is a round’s last step, not its first: run the plugin, sweep every page with the drift checker, fix upstream and re-run until the sweep is clean, then publish once. Every run consumers should see needs its publish; a round the sweep still faults is not one of them, however many unpublished changes the Assets panel counts.

The other runner, for one set at a time

The same reconciler can be driven through Figma’s MCP (use_figma) when a delta is small and the plugin is not at hand. build/mcp_figma.js cuts a release, a component, or one set into scripts that fit the tool’s 50,000-character limit, and --staged delivers the data in hash-checked segments parked in the file until the run script assembles them:

node build/mcp_figma.js card --sets=4 --staged       # one set: dist/figma/mcp/NNN-….stageK.js + .run.js, in index.json order
node figma-plugin/test/run-chunks.js                 # the slices, then the plugin on top, on the mock: it must create nothing

Validated 2026-09-04 in AODS_FigGen_4_1.0: button, badge and card applied through the MCP, the card’s chamfer fix re-applied as a delta (4 variants updated, nothing created), screenshots matching the browser. For a whole release the plugin is one click; the MCP is 74 scripts — use it for the delta, not the release.

Publishing

Publish only a release, never a half-applied one. Figma’s publish dialog lists every changed style, variable and component; that list should read like the apply summary. Write the version and source hash into the description so a consumer file’s “update available” can be traced to a build.

How do I know it’s right before everyone sees it? Learn more

What

A fix passes through three gates. The lint proves the system itself is still consistent. The reference pictures are the browser’s own rendering of the exact variants you touched, saved as images, so you can put them beside Figma’s. The mock is a pretend Figma that the plugin runs against in a second; it throws on the same mistakes the real Figma throws on, and it proves that applying the same release twice changes nothing. Only then does the release go to the real file, and only a whole release gets published.

Why

Publishing a library pushes the change to every file that uses it. A wrong publish is not one wrong drawing; it is a wrong drawing in every page across the team, with an “update available” prompt inviting everyone to take it. Checking one component in pictures and one apply on the mock costs minutes and stops that.

How

  1. Run the lint; it must report zero errors.
  2. Render the component you changed with --ref; look at the PNGs.
  3. Run the mock test for that component; it must say idempotent: YES.
  4. Apply to the library with only naming the component; screenshot the variants; compare to the PNGs.
  5. If it matches, apply the whole release (so the ledger and version are current) and publish with the version in the note.
Analogy — A print shop pulls one proof sheet and checks it under the light before running ten thousand copies. The reference PNG is the proof; publishing is the run.
