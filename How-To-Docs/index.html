Plain language

What is all this, and which parts should I care about? Learn more

What

A design system is a shared kit for building web pages: the colors, type, spacing and ready-made pieces (buttons, cards, forms) every page uses. A repository, or "repo," is the folder that kit lives in on GitHub, with a full history of every change. The design-system folder is the kit itself. The other folders let you see it (templates and documentation), learn it (this guide) and rebuild it (tools).

Why

Keeping the kit in one place means every page draws from the same source. Change the link color once and every page that uses the kit gets the new color. Without it, each team copies values by hand, and the copies slowly drift apart.

How

  1. Open templates/index.html to see full pages working, and documentation/index.html for every piece.
  2. Read design-system/README.md for the rules of use.
  3. Open a piece's folder in design-system/components for its guide.
  4. Leave the generated files (tokens.css, bundle.css, bundle.js) alone; they are rebuilt from the sources.

Analogy: it's a restaurant's recipe binder. The binder is the design system, the photos in it are the templates, and the kitchen notes on how the binder is printed are the tools. Cooks follow the binder; nobody rewrites the printed copies by hand.

Section 2 of 5

Load the system on a page

Technical

Load three files in this order. The script is optional: every component renders without it.

<link rel="stylesheet" href="design-system/tokens.css">
<link rel="stylesheet" href="design-system/components/bundle.css">
<script src="design-system/components/bundle.js" defer></script>

Every page starts from the same shell. .aods-page on <body> sets the ground, ink, focus ring and antialiasing once.

<body class="aods-page">
  <a class="aods-skip-link" href="#main">Skip to main content</a>
  <!-- site-alert (when there is one), header -->
  <main id="main" tabindex="-1">
    <section class="aods-ground">
      <div class="aods-layout" data-kind="container">
        <button class="aods-button" data-variant="primary" data-size="md">Apply now</button>
      </div>
    </section>
  </main>
  <!-- footer -->
</body>
  • Classes begin aods-; variants are data-* attributes; parts are __part classes.
  • AODS.init(root) wires markup injected after load. AODS.toast(message, { status, title, sticky }) and AODS.modal.open(id) are the page-facing calls.
  • Icons come from the sprite bundle.js inserts: <svg class="aods-icon" data-size="md" aria-hidden="true"><use href="#aods-search"></use></svg>.
  • Fonts load from tokens.css; keep design-system/fonts/ beside it.

Plain language

How does a web page actually start using the design system? Learn more

What

A web page is a text file of HTML: labeled boxes of content. On its own it looks plain. The three lines at the top point the page at the design system's files: tokens.css holds the values (colors, sizes), bundle.css holds the look of every piece, and bundle.js adds behavior such as menus that open and close. A "class" is the label that tells a box which piece it is, such as aods-button.

Why

Pointing at shared files instead of copying them means a page always gets the current version. The order matters because each file builds on the one before: the look needs the values, and the behavior needs the look.

How

  1. Put the three lines in the page's <head>, in that order.
  2. Give the <body> the label aods-page.
  3. Add pieces by copying their markup from each component's guide, then changing the words.
  4. Pick a variant by changing an attribute, for example data-variant="secondary" for a quieter button.

Analogy: it's like a new apartment. The three lines connect the utilities: water first, then power, then the internet. Once they're connected, every room you furnish already works.

Build a page

Technical

The page model
LayerMarkupRule
Groundsection.aods-ground[data-ground]A section. Carries the color edge to edge, holds content 32 from the window (16 at compact), no vertical padding.
Container.aods-layout[data-kind="container"]Sits in a ground, no fill, content 24 from the color, components 16 apart.
Paper.aods-paper[data-surface]A component with its own fill and paired stroke, inside a container.
Component.aods-*Always in a container, never directly on a ground.
  • Choose a component by the user's goal: design-system/choosing.md. It also lists what the system deliberately lacks (no carousels, no dark mode, no rounded corners outside the conversation family).
  • Start from a template: design-system/components/<Name>Template/ holds 15 full pages (shell, landing, program, article, newsroom, data, form, grant, search, emergency, assistant …).
  • Dark is a variant, never a page mode: a dark section is data-ground="dark", and each dark-capable component inside carries data-surface="dark". Light-only components (forms, tables, alerts, the conversation family) stay light.
  • Themes: a theme is one file, themes/<id>.json, declared as data-theme="<id>" on <html>. It swaps the four brand ramps and may swap the type family, label case, depth marks, shadow and radius base; the status ladder's structure never changes. The house is savory.
  • One h1 per page, as its first heading. No horizontal scrolling: wrap, fold or cut.

Plain language

How do I put a page together without breaking the rules? Learn more

What

Every page is a stack of bands. A band (a "ground") sets the background color across the full width. Inside each band, a "container" keeps the content a set distance from the edges. The pieces, such as buttons and cards, sit inside containers. A "template" is a finished example page you can copy.

Why

Fixed nesting keeps spacing identical from page to page, so pages feel like one site even when different people build them. The system also measures the space between bands for you, so nobody has to guess.

How

  1. Find the template closest to the page you need on the Templates page, and copy its markup.
  2. Replace the words and images; keep the bands, containers and pieces.
  3. If you need a piece the template lacks, look up the user's goal in choosing.md and copy that piece's markup from its guide.
  4. For a dark band, mark the band dark and mark each piece inside it dark too.

Analogy: it's packing moving boxes. The truck is the page, each box is a band, the packing paper is the container's margin, and the dishes are the pieces. Dishes never ride loose in the truck.

Tokens: the three tiers, and changing a value

Technical

Token tiers
TierPrefixHoldsLives inBound by
Global--g-Literal values: color ramps, scales, familiestokens.json (colors), bundle.css (the rest)The semantic tier only
Semantic--s-Meaning, with a light and a dark-surface valuetokens.jsonPage CSS
Component--c-The contract each component binds (1,763 tokens)components/bundle.cssComponents only

Change a value:

# 1. edit the value in design-system/tokens.json (shared) or themes/<id>.json (one theme)
# 2. regenerate the emitted files, the docs data and the templates
python3 tools/emit_tokens.py
python3 tools/build_docs.py
python3 tools/build_template_pages.py
# 3. check the reference page and the templates (add ?theme=<id> to a template), then commit
  • Never write a color, size, radius or font literal in page CSS; bind --s-*. If no token fits, report the gap.
  • A semantic color's dark-surface value is stored twice: the Dark surface legs in tokens.json (also emitted as [data-surface-scope="dark"]) and the data-surface="dark" scope (section 3) in bundle.css. Change both together.
  • Every text color's usage note in tokens.json states its measured contrast; keep 4.5:1 (3:1 for icons and large text).

Plain language

What is a token, and why are there three kinds? Learn more

What

A token is a named value, such as "the link color" or "the space between two cards." There are three layers of names. The bottom layer is the raw paint chips: every shade, numbered. The middle layer gives each job a name, such as "body text" or "page background," and points at a chip. The top layer says which job each part of each piece uses.

Why

Names by job let you change meaning safely. If body text should be a shade darker, you point "body text" at a different chip, and every piece that uses body text follows. The middle layer also holds a second answer for dark backgrounds, so a piece knows its dark colors without anyone deciding them one piece at a time.

How

  1. Find the token in tokens.json and change its value.
  2. Run the three commands shown above to rebuild.
  3. Open the reference page and a few templates and look at the pieces that use it, in light and on a dark surface, and under each theme the repository has.
  4. Commit the change with a sentence saying what changed and why.

Analogy: it's a paint store. The chips on the wall are the bottom layer; "kitchen walls" and "front door" on your shopping list are the middle layer. Repaint the front door by crossing out one chip number on the list, not by visiting every door.

Work with the system on GitHub

Technical

Change something

git clone https://github.com/puddnsnacks-hub/aods.git
cd aods
git switch -c darken-link-color
# edit, then: python3 tools/emit_tokens.py && python3 tools/build_docs.py && python3 tools/build_template_pages.py
git add design-system templates
git commit -m "Darken the link color one step"
git push -u origin darken-link-color

Open a pull request from the branch on GitHub; merge into main after review. main is the released state.

Release a version

git switch main && git pull
git tag v2.1.1 -m "Link color one step darker"
git push origin v2.1.1

Use it in another project

git submodule add https://github.com/puddnsnacks-hub/aods.git vendor/aods
# link vendor/aods/design-system/tokens.css, components/bundle.css, components/bundle.js
git submodule update --remote          # pull a newer version later

Host the site and this guide

The site lives in a separate repository, puddnsnacks-hub/aods-site, private until it is made public; once public, GitHub Pages serves it at aods.puddnsnacks.com. The source repository stays private. After a change is merged into main:

python3 tools/publish_site.py            # copies index.html, documentation/, templates/, How-To-Docs/, design-system/ and pushes
python3 tools/publish_site.py --dry-run  # counts what would change, pushes nothing

Never edit the site repository by hand; each publish replaces it. The domain is a CNAME record (aods → puddnsnacks-hub.github.io) at the domain registrar. Without the site, open index.html from a local clone.

The hosted design-system page

AODS does not publish to the hosted design-system page; design-system/ is the system itself, and the site above is its only publication.

Plain language

How do changes get from my computer to everyone else? Learn more

What

GitHub keeps the master copy of the repository online. "Clone" makes your own copy. A "branch" is a private draft where you make a change. A "commit" saves a step with a note. A "pull request" asks others to review your draft before it joins the master copy. A "tag" stamps a version number on a moment in history so other projects can ask for exactly that version.

Why

Drafts and reviews keep a half-finished change from reaching every page that uses the system. Version numbers let a project stay on a known version until it is ready to move up.

How

  1. Clone the repository once.
  2. For each change, make a branch, edit, rebuild, and commit with a clear note.
  3. Push the branch and open a pull request on GitHub; ask a teammate to review it.
  4. After it merges, tag a new version if other projects should pick it up.
  5. To update the public site, run the publish script. Everything in the site is public; the source stays private.

Analogy: it's a shared cookbook at a library. You borrow a copy, write your edits on sticky notes, and hand them to the librarian. Only after a second reader agrees do the notes go into the book, and each printing gets an edition number.
